# 技能以系统提示元数据的形式暴露，而不是注册成工具

li 需要支持技能：写在 `SKILL.md` 里的做事方法，用户在 `~/.agents/skills` 和项目内的 `.agents/skills` 下自备。实现上至少有三条路——每个技能注册成一个工具、实现 `skill://` 内部协议、只把名字和描述放进系统提示让模型自己读正文。我们选择第三条，因为系统提示的体积要随技能数量增长，但增长速度必须远小于工具定义；技能没有参数也没有返回值，本来就不构成工具接口。

## 考虑过的方案

- **每个技能注册成一个工具**：工具定义每次请求都要发给模型，技能越多提示越长；而技能是文档，不是可调用接口。
- **`skill://` 内部协议**（omp 的做法）：要让模型能读技能目录下的脚本和模板，需要额外实现名称解析、路径越界校验、内容类型推断。绝对路径配合现有 `read` 工具已经能表达同样的事。
- **只做斜杠命令调用**：需要用户先知道技能名字，且模型无法自己判断"这个任务该用哪个技能"。作为补充手段保留，但不能替代按需读取。

## 后果

模型可能读到与当前任务无关的技能正文，浪费上下文——这是按需读取的固有代价，靠 `description` 写得准确来缓解。系统提示每多一个技能只增加几十个字，二十个技能约等于一段项目规则的长度。

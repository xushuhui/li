# li — 设计文档

用 Rust 重写的终端 coding agent，只保留 omp 真正被使用的那一层：主循环（agent loop）、会话持久化、上下文压缩、LSP。

项目名取自《易》第三十卦「离」——离为火，为明，为目：火照见东西，目认出东西。只有主程序叫 `li`，其余模块按英文单词命名。

状态：草案，尚未实现。

---

## 1. 背景

omp 现在的成本（在 16 GB 的 Mac 上实测）：

| 维度 | 数值 | 构成 |
|---|---|---|
| 单实例常驻内存 | 400–660 MB | Bun 运行时 + `pi_natives.darwin-arm64.node`（160 MB 原生模块）+ TUI |
| 磁盘 | 约 1.2 GB | 主程序 199 MB + 原生模块 160 MB + 会话记录 477 MB |
| 命令面 | 50+ 个 | 其中日常使用不到 10 个 |
| 工具面 | 14 个 | 其中 DAP 从未使用 |

根因不是"功能太多所以重"，而是架构决定的：TypeScript 主体需要一个 JS 运行时，重活交给一个 160 MB 的 Rust 附加模块。裁剪配置改变不了这个数字——把扩展、技能、LSP、规则全关掉，实测内存仍在 400–700 MB 之间波动。

omp 的会话存储是一棵树，不是一条线——每个条目带 `id` 和 `parentId`。这个结构开销很小，并且让上下文压缩、崩溃恢复、"回到压缩前的某个点"都变得简单。

但"从历史节点分叉继续"这个交互，实际使用中从未发生过（用户自述没用过 `/tree`）。所以 li 保留树的**数据结构**，不把树的**界面操作**放进第一版。

li 的目标：保留主循环和这套存储模型，用 Rust 重写成单二进制，其余全部不要。

---

## 2. 目标与非目标

### 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 空闲常驻内存低于 60 MB | 启动后空闲 10 秒读进程 RSS |
| G2 | 冷启动到可输入低于 50 ms | 二进制启动到首屏 |
| G3 | 会话持久化与恢复：关掉后能继续上次对话 | `--continue` 恢复最近会话，消息完整 |
| G4 | 崩溃安全：进程被 `kill -9` 后会话不丢 | 强杀后重新打开，之前的消息完整 |
| G5 | 六个核心工具 + LSP | 端到端完成一次真实改动 |
| G6 | 单一二进制，无运行时依赖 | 拷到另一台同架构机器直接跑 |

### 非目标

明确不做，不是"以后再说"：

- N1 DAP 调试协议（用户使用 dlv 命令行，不需要 agent 代劳）
- N2 插件市场、技能注册表
- N3 多机协作、会话直播、分享链接
- N4 浏览器自动化、桌面控制
- N5 语音合成与识别
- N6 Notebook 编辑、Python 内核
- N7 富终端界面（第一阶段用流式输出，TUI 见里程碑 M6）
- N8 图片输入（第一版不做，见 D23）

## 3. 设计决策

每个决策列出一个被否决的真实备选，以及否决理由。

### D1 会话存储：追加写 JSONL，每个条目带 `parentId`

**选择：** 每个会话一个 `.jsonl` 文件，每行一个条目，条目之间用 `id` / `parentId` 组成树。当前可见的上下文 = 从"叶子指针"沿 `parentId` 回溯到根的那条路径。

**被否决的备选：SQLite 单表存储。**

否决理由：SQLite 引入约 3 MB 依赖和 schema 迁移负担，而单用户的会话量（几百个文件）用文件系统足够。读一条会话只需要顺序读一个文件。代价是"列出所有会话"要扫描目录，用 D2 补偿。

**被否决的备选二：纯内存 + 退出时快照。**

否决理由：违背 G4。强杀进程会丢掉整个会话。

### D2 会话索引：第一阶段不做，第二阶段加 sidecar

第一阶段直接 `glob` 会话目录 + 读每个文件的第一行（会话头）。几百个文件的目录扫描在 20 ms 内完成。

当会话数超过约 2000 个时，再加一个索引文件（`index.json` 或 SQLite），记录 `会话ID → 标题、cwd、最后修改时间、大小`。

### D3 异步运行时：tokio

**理由：** 模型请求是网络 IO，工具调用里有 `bash` 这类长时间子进程，且需要并行执行同一轮的多个 `toolCall`（模型一次返回 3 个读取请求，应该并发而不是串行）。

**被否决的备选：同步 + rayon 线程池。**

否决理由：网络请求需要超时、取消、流式读取，线程池要自己实现这些，等于重造 tokio 的子集。

### D4 工具接口：`async trait`，每个工具自带 JSON Schema

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    fn name(&self) -> &'static str;
    fn description(&self) -> &'static str;
    fn schema(&self) -> serde_json::Value;
    async fn execute(&self, args: serde_json::Value, ctx: &ToolContext) -> ToolOutcome;
}
```

`ToolOutcome` 包含：输出文本、是否出错、可选的附加数据（例如编辑前后的 diff）。

**理由：** Schema 由工具自己产出，交给模型时直接序列化，不需要手写第二份定义。

### D5 上下文压缩：摘要替换，保留原条目

上下文接近上限时，生成一个 `compaction` 条目：

```json
{"type":"compaction","id":"...","parentId":"...","summary":"## Goal\n...\n## Constraints\n..."}
```

这条记录成为新的上下文起点。**原有消息不删除**——它们还在文件里，树结构不变，所以任何时刻都能回到压缩前的任意节点（界面层面排在 M8）。

**被否决的备选：直接丢弃最早的消息。**

否决理由：丢掉的往往正是任务目标（用户开头说的话），导致 agent 在压缩后重复已经排除的方案。

### D6 前端：先流式文本，后 TUI

第一阶段：直接往标准输出写，工具调用用一行摘要表示。理由是先验证核心循环，界面是独立问题。

第二阶段（M6）：引入 `ratatui` 做分屏。**被否决的备选：一开始就做 TUI**——会把调试核心逻辑的成本放大三倍。

v2 修订：stdin 和 stdout 都是终端、且没有传入 PROMPT 参数时，默认为全屏界面；不再需要 `--tui` 开关。管道输入与单轮调用仍是纯文本。**被否决的备选：保留 `--tui` 开关、纯文本为默认。** 否决理由：实际使用时每次都要多敲四个字符，而唯一需要纯文本的场景（管道、单轮）本身就不会进交互循环。

### D7 模型协议：先做 OpenAI 兼容，后加 Anthropic

用户的主力模型走本地网关（`http://127.0.0.1:3425/v1`，OpenAI 兼容、无密钥）。一套协议能覆盖 90% 的日常使用。

Anthropic 原生协议（用于 cache 控制）放到 M8。

### D8 token 计数：字符估算 + 真实用量校正

请求前按字符估算（中文 1 字符约 1 token，英文与代码 4 字符约 1 token）判断是否接近阈值；收到响应后用模型返回的 `usage.input` 校正累计值。

**被否决的备选：引入 `tiktoken-rs`。** 否决理由：它只准确覆盖 OpenAI 的分词器，而主力模型是 DeepSeek 系；为 10% 的精度引入数 MB 依赖不划算。

### D9 配置：TOML，放在 XDG 目录

路径 `~/.config/li/config.toml`（该目录在你的机器上已是 dotfiles 仓库的软链，配置自动纳入版本管理）。

```toml
[model]
default = "workbuddy/deepseek-v4.1-flash"
base_url = "http://127.0.0.1:3425/v1"
context_window = 1000000
# api_key 默认从环境变量 LI_API_KEY 读取，不写进文件

[context]
compact_at_percent = 80

[tools]
bash_approval = "prompt"   # prompt | allow

[project]
rules_file = "AGENTS.md"
```

**被否决的备选：YAML（与 omp 一致）。** 否决理由：TOML 在 Rust 生态是主流，`serde` 支持最成熟，且没有 YAML 的缩进歧义。

### D10 项目规则：逐层读取 `AGENTS.md`

启动时从当前工作目录向上走，每一层的 `AGENTS.md` 都读，直到仓库根（第一个含 `.git` 的目录，含它本身）为止。按从外到内的顺序追加到系统提示，每段标注来源路径；子目录的规则排在后面，更靠近当前工作位置。

**被否决的备选：只读最近的一个（原方案）。** 否决理由：monorepo 里子目录有自己的 `AGENTS.md` 时，仓库根那份被静默忽略，而根文件通常放的是全局构建与提交流程。

**被否决的备选：兼容 `CLAUDE.md` / `.cursorrules` / `copilot-instructions.md`。** 否决理由：多来源必然出现规则冲突（两份文件对同一件事要求相反），单一约定更容易维护。

### D11 写入安全：依赖 git，不自建备份

`edit` / `write` 自动执行，不弹确认。每次工具调用前在内存里记录 `git status --porcelain` 快照；用户要求撤销时，用 `git checkout -- <files>` 或 `git clean -fd` 恢复。

`bash` 在非白名单命令时暂停，读一个 `y/n`。

**被否决的备选：自建文件备份目录。** 否决理由：目标项目都是 git 仓库，git 已提供完整的快照与恢复能力，再实现一套只会产生两份不一致的历史。

### D12 异常处理：重试三次，重复三次即中断

模型请求失败（超时、429、5xx）按 1s / 2s / 4s 退避重试，三次后终止本轮并提示。不做模型切换。

同一工具 + 完全相同参数的调用连续出现 3 次，中断并在会话中说明原因。

**被否决的备选：模型 fallback 链（omp 的做法）。** 否决理由：第一版只配一个模型，fallback 链要维护多个 provider 的凭证与能力差异，收益低于成本。

### D13 单模型

第一版只有一个 `model.default`，`--model` 可临时覆盖。不做 smol / slow / plan 角色分工。

**被否决的备选：多角色（omp 的做法）。** 否决理由：主力模型本身兼顾速度与成本，角色分工省不下可观的费用，却让配置和状态机复杂度翻倍。

### D14 会话文件组织与选择

路径：`~/.li/sessions/<编码后的目录>/<时间戳>_<短ID>.jsonl`，目录编码沿用 omp 的方式（`/Users/xsh/gp/dotfiles` → `-Users-xsh-gp-dotfiles`）。

`--continue` 取当前目录下最新的一个；`--resume` 不带参数时打印最近 10 个（编号、标题、时间、目录），输入编号选择。

**被否决的备选：全部平铺在一个目录里按时间排序。** 否决理由：在项目间切换时，混合列表里大半是无关会话。

### D15 上下文窗口：由配置声明

`[model] context_window` 显式声明模型能吃的 token 数，压缩阈值按它的百分比计算。

**被否决的备选：硬编码已知模型表，或按模型名正则猜测。** 否决理由：主力是自定义网关模型，任何内置表都认不出它；猜错会导致压缩过早或上下文溢出。

### D16 工具并行边界

同一轮的多个 `toolCall` 分两类执行：只读工具（`read`、`grep`、`glob`）并行；有副作用的工具（`write`、`edit`、`bash`）串行，且严格保持模型给出的顺序。

**被否决的备选：全部并行。** 否决理由：模型经常在一轮里同时发"改文件"和"跑测试"，并行执行会让测试读到改之前的内容。

### D17 中断语义

第一次 `Ctrl+C`：中断当前的流式输出或正在运行的命令，回到输入提示符，进程不退出。1 秒内再按一次：退出进程。

被中断的工具调用必须补一个 `isError: true` 的 `toolResult`（内容为"用户中断"），维持成对不变量。

**被否决的备选：`Ctrl+C` 直接退出进程。** 否决理由：长任务进行中误触会打断整个交互，而进程重启至少要重新加载会话。

### D18 输出形态（第一阶段）

模型文本逐块写到标准输出，markdown 原样呈现，不做语法高亮。工具调用显示一行摘要 `▶ grep "foo" in src/`。工具结果只在出错或超过 5 行时显示首尾各 3 行；完整内容只写入会话文件。

**被否决的备选：等完整响应再一次性打印。** 否决理由：长时间生成时终端没有反馈，用户无法判断是卡住还是在工作。

### D19 LSP：只用系统已装，惰性启动

不下载、不管理 LSP server。找不到 `gopls` 或 `typescript-language-server` 时报告错误并给出安装命令。第一次调用 LSP 工具时才启动对应语言的 server，5 分钟无调用则关闭。

**被否决的备选：随 li 自动下载 server 二进制。** 否决理由：下载、版本管理、完整性校验是一整套工程，而目标机器上这些 server 通常已经装好。

### D20 语言检测：项目根标记 + 文件扩展名

项目根由 `git rev-parse --show-toplevel` 确定。根目录的标记文件（`go.mod`、`package.json`、`Cargo.toml`）决定启动哪些 server；具体调用哪个 server 由目标文件的扩展名决定。

**被否决的备选：只看文件扩展名。** 否决理由：无法确定 workspace root，而 LSP 的初始化参数需要它。

### D21 多行输入

回车发送。粘贴内容里的换行原样保留，不触发发送。手动换行用 `Alt+Enter`。

**被否决的备选：回车换行、`Ctrl+D` 发送。** 否决理由：与大多数终端工具的肌肉记忆相反，且粘贴多行代码时更容易误发。

### D22 会话标题：取首条用户消息

标题取第一条用户消息的前 40 个字符，不调用模型。

**被否决的备选：调用模型生成标题（omp 的做法）。** 否决理由：多一次请求；自动标题在中文场景经常比原文更模糊。

### D23 图片输入：第一版不做

模型配置声明支持图片，但网关是否真的接受尚未验证。等核心闭环跑通、确认网关可接收之后作为独立里程碑加入。

**被否决的备选：第一版就支持。** 否决理由：粘贴、编码、消息格式三处都要改，而它不属于核心场景。

### D24 全局规则文件

读取 `~/.config/li/AGENTS.md` 作为全局规则，追加到系统提示。优先级从低到高：内置提示 < 全局规则 < 项目 `AGENTS.md`。

**被否决的备选：把回复偏好（中文、首词"辉哥"）硬编码进系统提示。** 否决理由：偏好是稳定事实但会变化，写在文件里不需要重新编译。

### D25 不做项目级配置

第一版只有全局 `~/.config/li/config.toml`，项目差异用命令行参数覆盖。

**被否决的备选：支持 `<repo>/.li/config.toml`。** 否决理由：它解决的是"换项目自动换模型"，而当前没有这个需求；先加会引入配置优先级与冲突合并这一整块复杂度。

### D26 会话文件健壮性

读取时跳过解析失败的行，在标准错误输出警告，不静默忽略。写入时对会话文件加排他锁（`<文件>.lock`）；第二个实例尝试 `--continue` 同一会话时报错并列出可选项，但允许开新会话。

**被否决的备选：遇到损坏就拒绝打开会话。** 否决理由：强杀进程必然留下半行 JSON，拒绝打开等于让最需要恢复的场景失效。

### D27 分发：手动拷贝

`cargo build --release` 后拷贝到 `~/.local/bin/li`。不发布到 crates.io，不做 Homebrew tap。

**被否决的备选：一开始就做 Homebrew tap。** 否决理由：分发是稳定之后的事，先验证它真的能替代日常使用。

### D28 编辑：行内锚点，不做旧文本匹配

`read` 的输出带一个 `[路径#标签]` 头，标签是文件内容规范化后的 4 位十六进制摘要；同时把这份内容快照记在会话内存里。`edit` 的输入不是"旧文本/新文本"，而是带同一个头的行操作：

```
[src/main.rs#1A2B]
PUT 4.=4:
+let value = 2;
```

操作集合：`PUT N.=M:`（替换第 N 到 M 行）、`PUT <N:` / `PUT >N:`（在第 N 行前后插入）、`PUT >$:`（追加到文件尾）、`CUT N.=M`（删除）。标签与当前文件内容不匹配时拒绝执行并要求重读；只允许编辑快照记录过的行范围。

**被否决的备选：旧文本唯一匹配（原计划）。** 否决理由：模型经常在旧文本里漏一个空格或缩进，导致找不到匹配或匹配到错误位置，而它无法从错误信息里可靠地修复；大段改动还要求模型完整重述旧内容，token 消耗高。锚点把"读过什么"变成可验证的事实，模型不能编辑它没看过的行。

**被否决的备选：完整 omp hashline（含语法块锚点 `N*`、命名寄存器、`MV`/`REM`）。** 否决理由：语法块锚点依赖 tree-sitter 的多语言解析，是独立工程；M2 只需覆盖"改一个函数"的场景，寄存器与移动可以用 `write` 和 `bash` 替代。语法块锚点列入 v2。

### D29 斜杠命令：只有固定的几条，未知的照常发给模型

交互模式和 TUI 在把输入发给模型之前，先看第一个词是不是已注册的斜杠命令。v2 注册三类：`/init`（生成 `AGENTS.md`）、`/help`（列出可用命令），以及每个已发现技能对应的 `/skill:<技能名>`。以 `/` 开头但既不在注册表里、也不匹配 `skill:` 前缀的输入（例如 `/usr/local/bin` 这样的路径）不拦截，原样当用户消息发给模型。

**被否决的备选：可扩展的命令注册点（omp 的 `registerCommand`）。** 否决理由：命令集合是固定的——`/skill:` 这一族直接由技能目录决定，不需要外部注册；注册点还要配套发现顺序、重名冲突处理、帮助列表生成，维护成本远超收益。

**被否决的备选：做成 CLI 子命令 `li init`。** 否决理由：生成 `AGENTS.md` 之后通常要接着让模型改，子命令跑完就退出，得重开一次会话。

实现状态：`/help`、`/exit`、`/init`、`/skill:<名字>` 已落地。输入框里以 `/` 开头时，状态栏列出模糊匹配的命令（前缀匹配排在前，其余按字符顺序匹配），第一个为选中项，按 Tab 填入；最多显示 6 条，超出时显示总数。

### D30 技能：系统提示只放名字和描述，正文由模型自己读

启动时扫描 `~/.agents/skills/*/SKILL.md`，以及从当前目录到仓库根每一级的 `.agents/skills/*/SKILL.md`。每个技能的 `name` 和 `description` 拼成一段放进系统提示，同时给出 `SKILL.md` 的绝对路径；模型判断某个技能相关时，用现有 `read` 工具打开正文。同名技能离当前目录越近优先级越高。

**被否决的备选：每个技能注册成一个工具。** 否决理由：工具定义每次请求都要发给模型，技能越多提示越长；而技能没有参数、没有返回值，不构成工具接口。

**被否决的备选：`skill://` 内部协议（omp 的做法）。** 否决理由：要额外实现名称解析、路径越界校验、内容类型推断三套逻辑；绝对路径已经能表达同样的事，而 `read` 工具现成。

用户也可以主动点名：`/skill:<名字> [参数]` 读出 `SKILL.md` 全文、剥掉 frontmatter，把正文和技能目录的绝对路径一起作为一条用户消息注入，参数附在正文末尾。注入的是一次性消息，不写进系统提示，所以不占常驻预算。

技能块有两条硬线：单个描述截到 100 字符，最多列出 64 个；被截掉的部分在块末写一句"另有 N 个未列出，可用 `/skill:` 调用"。它放在项目规则之后——越靠末尾的常驻内容，在长对话里越不容易被忽略。相应地，系统提示与工具定义的预留量从 800 调到 1200 个 token，上下文压缩的估算跟着变。

扫描只在启动时做一次。会话中途新建的技能要重开会话才生效——目录监听、增量刷新、hash 比对都是额外工程，而写技能是低频动作。

实现状态：已落地。`/skill:` 注入随 D29 的斜杠命令层一起实现。

### D31 `/init`：让模型读代码后直接写出 `AGENTS.md`

在仓库根目录执行：把一条内置提示词作为用户消息发出，允许模型用 `read`、`glob`、`grep` 探索，然后由它调用 `write` 生成根目录的 `AGENTS.md`。内容限定四段：项目用途、构建与测试命令、目录约定、已知陷阱。文件已存在时拒绝执行，提示用户自己处理。

不允许执行命令（`bash`）：`/init` 的成败不该取决于机器上有没有装对应的构建工具，读 `Cargo.toml`、`package.json`、`Makefile` 已经能拿到构建与测试命令。

**被否决的备选：先生成给用户看，确认后再落盘。** 否决理由：多一次交互；文件生成后本来就能直接打开看，不满意重跑一次比重看一遍确认更快。

**被否决的备选：固定模板填空，不调用模型。** 否决理由：填出来的只有仓库名和构建工具，而"这个仓库的约定"恰恰是模型读代码才能得出的部分。

实现状态：已落地（`/init`，模型自己判断何时调用 `write`；`AGENTS.md` 已存在时直接拒绝，不调模型）。

### D32 固定开场白写成 `system_prompt.md`，模型名进提示

内置的四行（身份、工作目录、时间、模型）存在 `crates/core/src/system_prompt.md`，用 `include_str!` 编译进二进制，运行前替换 `{{cwd}}`、`{{now}}`、`{{model}}` 三个占位符。规则块与技能块仍由代码拼接——它们有条件、截断和计数，用模板表达比直接拼更绕。

模型名进提示是为了让模型知道自己在哪个模型上运行；不写的话，被问到时它会按训练数据里的身份回答（DeepSeek 会说自己是 Claude）。

**被否决的备选：运行时读取 `~/.config/li/system_prompt.md`，内置版本作兜底。** 否决理由：多一条分支和一个静默失败点——文件写坏时行为变了但不报错；而改提示词是低频动作，重新编译只要十秒。

**被否决的备选：整段提示做成一个模板文件，规则与技能也走占位符。** 否决理由：技能块需要按数量截断、按长度截断、末尾追加计数，把这三件事塞进模板语言，读起来比 Rust 代码更费解。

### D33 状态栏：左边是位置，右边是代价

最后一行常驻四样东西，左对齐和右对齐各一组：

```
~/gp/li  main *3                                    35%  1M  workbuddy
└ 目录与 git 状态（分支 + 改动文件数）                 └ 上下文占用、窗口大小、模型
```

- **上下文占用**取最近一条助手消息里的 `usage.input` 除以配置的 `context_window`：那个数字就是这次请求发过去的全部 token，即当前上下文的实际大小。跨轮不需要重新统计，压缩后自动回落。
- **git 状态**用 `git rev-parse --abbrev-ref HEAD` 和 `git status --porcelain` 现算：启动一次，每轮结束一次。放在轮次之间，不在请求中途，阻塞几十毫秒无所谓。
- **优先级**：危险命令确认 > 斜杠候选 > 临时状态文字（报错、压缩提示）> 信息栏。临时文字在下一轮开始时清空，把这一行还给信息栏。
- 宽度不够时先丢掉模型名，再让终端截断；右半边永远贴右边缘，所以左右两组的距离随窗口宽度变化。

**被否决的备选：每帧重算（在 `draw` 里读会话和跑 git）。** 否决理由：`draw` 每秒可能调用几十次，git 子进程每次几十毫秒，会把界面拖成卡顿；而这些数字只在轮次之间变化。

**被否决的备选：把信息栏做成可配置的段落。** 否决理由：只有一个用户、一份配置，四段内容都很短；做成配置就得处理顺序、宽度、缺省值，收益是零。

```
li/                        # Cargo workspace

├── specs/
```

依赖方向：`cli` → `core` → `provider` + `tools`；`lsp` 被 `tools` 使用（注册成工具）。

每个 crate 名沿用 Cargo 惯例加前缀 `li-`，内部模块用纯英文单词（`session`、`tree`、`loop`、`context`、`compact`）。

## 5. 数据模型

### 5.1 条目类型

第一版只实现前四种，后三种是可选统计：

| `type` | 作用 | 第一版 |
|---|---|---|
| `session` | 会话头：`id`、`cwd`、`version`、创建时间 | 必须 |
| `message` | 对话条目，`message.role` 为 `user` / `assistant` / `toolResult` | 必须 |
| `compaction` | 摘要替换点 | 必须 |
| `model_change` | 模型切换记录 | 必须 |
| `title` | 会话标题 | 可选 |
| `model_usage` | token 与成本统计 | 可选 |
| `custom` | 扩展注入的内容 | 不做 |

### 5.2 消息结构

助手消息：

```json
{
  "type":"message","id":"2d279b08","parentId":"b6bc5f58","timestamp":"2026-10-14T03:10:24.989Z",
  "message":{
    "role":"assistant",
    "content":[
      {"type":"text","text":"先看一下配置"},
      {"type":"toolCall","id":"call_1","name":"grep","arguments":{"pattern":"\\bghs\\b","path":"config"}}
    ],
    "usage":{"input":4,"output":103}
  }
}
```

工具结果消息（也是一个 `message`，只是 `role` 不同）：

```json
{
  "type":"message","id":"...","parentId":"2d279b08","timestamp":"...",
  "message":{
    "role":"toolResult",
    "toolCallId":"call_1",
    "toolName":"grep",
    "content":[{"type":"text","text":"config/zsh/functions.zsh:55: ..."}],
    "isError":false
  }
}
```

### 5.3 树与叶子

```rust
pub struct Session {
    entries: Vec<Entry>,          // 文件顺序，只追加
    index: HashMap<EntryId, usize>,
    leaf: EntryId,                // 当前可见路径的末端
}

impl Session {
    /// 从叶子沿 parentId 回溯到根，返回正序路径。
    /// 遇到 compaction 条目时停止回溯，把它作为新起点。
    pub fn visible_path(&self) -> Vec<&Entry>;
}
```

`visible_path()` 是上下文构建的唯一入口。树上的其他分支只影响"能不能跳回去"，不影响当前对话。

## 6. 主循环

```
loop {
    let ctx = build_context(session.visible_path(), system_prompt, tools);
    let response = provider.complete(ctx).await?;
    session.append(Message::Assistant(response.clone()));

    if response.tool_calls.is_empty() {
        break;
    }

    // 只读工具并行；有副作用的工具按模型给出的顺序串行（D16）
    let results = execute_batch(&tools, response.tool_calls).await;

    for r in results {
        session.append(Message::ToolResult(r));
    }

    if context_tokens(&session) > compact_threshold {
        let summary = provider.summarize(&session).await?;
        session.append(Compaction::new(summary));
    }
}
```

三个不变量：

1. **每条消息必须先落盘再发给模型**。这样强杀进程时，已发生的对话一定完整。
2. **`toolCall` 与 `toolResult` 必须成对**。如果进程在中间被杀，下次打开时发现没有结果的 `toolCall`，补一条"执行被中断"的结果，而不是丢给模型一个错误的状态。
3. **压缩后不删除任何条目**，只追加一个 `compaction`。

## 7. 工具规格

| 工具 | 输入 | 输出约束 | 可并行 |
|---|---|---|---|
| `read` | 路径、可选行范围 | 输出带 `[路径#标签]` 头与行号；超过 2000 行时截断并提示剩余行数 | 是 |
| `write` | 路径、完整内容 | 覆盖写，返回字节数 | 否 |
| `edit` | `[路径#标签]` + 行锚点操作 | 标签必须匹配最近一次读取；只允许编辑已读过的行范围 | 否 |
| `grep` | 正则、路径、可选文件过滤 | 最多 100 条命中，超出提示收窄范围 | 是 |
| `glob` | 模式 | 最多 200 条，按修改时间倒序 | 是 |
| `bash` | 命令、超时 | 输出超过 2000 行或 200 KB 时截断到摘要 + 首尾片段 | 否 |

`bash` 默认需要用户确认（除只读命令白名单：`ls`、`cat`、`git status`、`git diff`、`grep`、`find`、`rg`、`fd`）。配置里可切换为全自动。

LSP 不是单独的工具，而是注册三个：`lsp_diagnostics`（打开文件后的错误）、`lsp_definition`（跳定义）、`lsp_references`（找引用）。

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 | 模型客户端 + 消息模型 + 单轮流式输出 | `li "你好"` 能拿到回复并写入会话文件 |

## 10. 风险

| 编号 | 风险 | 应对 |
|---|---|---|
| R1 | LSP 客户端复杂度被低估：要处理 server 启动、初始化握手、每种语言不同的能力集 | 第一版只支持 Go 和 TypeScript 的 server；其他语言按需加 |
| R2 | 摘要压缩丢关键信息，导致 agent 重复犯错 | 摘要模板固定五段（目标、约束、已完成、待办、关键文件），不依赖模型自由发挥 |
| R3 | 大文件或长输出撑爆上下文 | 所有工具输出都走统一的截断层（第 7 节的约束），并有硬上限 |
| R4 | 平台差异 | 第一阶段只做 macOS；`bash` 直接复用系统 shell，不做 Windows 兼容 |
| R5 | 与 omp 并行使用时，两边会话互不相通 | 接受。li 写自己的 `~/.li/sessions/`，不读也不写 omp 的数据 |

## 11. 成功标准

项目算成功，当且仅当：

1. 在一个真实仓库里，li 独立完成"读懂代码 → 改一个函数 → 跑测试 → 修到通过"的完整闭环。
2. 空闲常驻内存低于 60 MB（对照 omp 的 400–660 MB）。
3. 会话文件可以用 `jq` 逐行读出，不需要任何专用工具。
4. 强杀进程后重开，最后一条消息还在。

四条都必须达成。li 的定位不是"功能更多"，而是"同样的活，用十分之一的内存和零配置完成"。

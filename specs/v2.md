# li v2 功能文档

v1 的目标：能替代 omp 完成日常编码工作（里程碑 M1–M7）。
v2 的目标：在 v1 已经稳定使用的前提下，补上被显式推迟的能力。

**进入 v2 的唯一标准：触发条件被真实满足。** 没有触发条件的条目不是功能，是愿望。本文档的每一项都必须能被"什么时候做"回答，否则不该留在这里。

**例外：2.10 与 2.11 由用户显式提出，不满足上述标准。** 留在本文档里是为了复盘：如果这两项上线后很快闲置，说明标准本身是对的，以后该按标准拒绝同类请求；如果天天在用，说明标准漏掉了"工具本身的易用性"这一类理由，该改标准。

---

## 1. v1 的边界

| 包含 | 不包含 |
|---|---|
| 主循环、六个工具、LSP（M1–M5） | 树操作界面（M8） |
| 会话持久化、崩溃恢复、上下文压缩 | 图片输入 |
| 流式 CLI 输出（M1） | 多模型角色 |
| TUI（M6） | 项目级配置 |
| Anthropic 原生协议、prompt cache（M7） | 会话索引 |
| 全局 + 项目 `AGENTS.md` | LSP server 自动下载 |
| | 模型 fallback 链 |

v1 完成的标志见设计文档第 11 节的四条成功标准。

---

## 2. v2 候选

按触发条件的可观测程度排序——越容易判断"该做了"的排越前。

### 2.1 树操作界面（`/tree`、`/branch`）

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 用户自述从未使用过 omp 的这个功能 |
| 触发条件 | 实际出现"想回到三轮之前、换另一条路重试"的需求，并且用手动编辑会话文件解决过 |
| 预估工作量 | 小。数据格式从第一天就有 `parentId`，只缺选择器和分支切换 |
| 依赖 | 无 |

### 2.2 项目级配置（`<repo>/.li/config.toml`）

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 单用户场景下没有"换项目自动换模型"的需求 |
| 触发条件 | 出现两个项目需要不同模型 / 不同审批策略，且每次手动加 `--model` 已经烦到影响使用 |
| 预估工作量 | 小。合并逻辑与 `AGENTS.md` 的两层结构一致 |
| 依赖 | 无 |

### 2.3 图片输入

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 网关是否接受 `image` 内容尚未验证 |
| 触发条件 | 先验证网关能收图片；验证通过后，出现"截图比文字描述更快"的实际场景（调样式、看报错截图） |
| 预估工作量 | 中。粘贴捕获、base64 编码、消息格式三处 |
| 依赖 | 网关验证 |

### 2.4 多模型角色（`smol` / `slow` / `plan`）

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 主力模型兼顾速度与成本，角色分工省不下可观的费用 |
| 触发条件 | 连续两个月账单显示单一模型成本明显偏高，或某些任务（长规划、提交信息生成）明显该用更便宜的模型 |
| 预估工作量 | 中。配置结构、选择逻辑、`--model` 覆盖语义都要扩展 |
| 依赖 | 无 |

### 2.5 会话索引（D2 的 sidecar）

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 几百个文件的目录扫描在 20 ms 内完成，索引是过早优化 |
| 触发条件 | `~/.li/sessions` 下会话文件数超过 2000，或目录扫描实测超过 100 ms |
| 预估工作量 | 小。一个 `index.json` 或 SQLite 表 |
| 依赖 | 无 |

### 2.6 模型 fallback 链

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 只配一个模型，fallback 要维护多 provider 的凭证与能力差异 |
| 触发条件 | 主力模型出现持续不可用时段（> 30 分钟），且这段时间里被迫中断了工作 |
| 预估工作量 | 中。凭证管理、能力探测、失败判定 |
| 依赖 | 至少第二个可用 provider |

### 2.7 LSP server 自动下载

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 下载、版本管理、校验是一整套工程；目标机器上 server 已经装好 |
| 触发条件 | 换第二台机器时，手动安装 server 的步骤重复了三次以上 |
| 预估工作量 | 中 |
| 依赖 | 无 |

### 2.8 压缩摘要质量改进

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 先按固定五段模板跑，观察实际效果 |
| 触发条件 | 压缩之后出现重复犯错：重新尝试已被排除的方案，或忘记用户最初的约束 |
| 预估工作量 | 中。可能需要针对失败案例调整模板，或保留更多原文 |
| 依赖 | 真实使用中的失败样本 |

### 2.9 语法块锚点（`PUT N*:`）

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 依赖 tree-sitter 的多语言解析，是独立工程 |
| 触发条件 | 行锚点编辑在真实修改中反复出现"必须数行号才能定位一个函数"，一周内遇到三次以上 |
| 预估工作量 | 大。每种语言需要对应的 grammar |
| 依赖 | tree-sitter 与语言 grammar |

### 2.10 斜杠命令 `/init`：生成 `AGENTS.md`

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 交互模式只有"发消息给模型"一条路径，没有任何输入分流 |
| 触发条件 | **用户显式要求**（不满足触发条件标准，见文首的例外说明） |
| 预估工作量 | 小。输入分流加一条内置提示词 |
| 依赖 | 斜杠命令层（design.md D29） |

行为：在仓库根目录让模型读代码后写出 `AGENTS.md`，内容包括项目用途、构建与测试命令、目录约定、已知陷阱四段。生成过程不执行 shell 命令，只读文件。文件已存在时拒绝覆盖，提示用户先自行处理（design.md D31）。

### 2.11 技能调用

**状态：已实现**（元数据与 `/skill:<名字>` 注入；`/init` 仍未做）。

| 项 | 内容 |
|---|---|
| v1 为什么没做 | 首版目标是核心闭环，技能属于能力扩展 |
| 触发条件 | **用户显式要求**（不满足触发条件标准，见文首的例外说明） |
| 预估工作量 | 小。扫描目录、读 `SKILL.md` 的 frontmatter、拼进系统提示 |
| 依赖 | 无 |

行为：启动时扫描 `~/.agents/skills` 和项目内各级 `.agents/skills`，把每个技能的 `name` 和 `description` 放进系统提示，正文由模型用 `read` 按需读取。用户可以用 `/skill:<名字> [参数]` 主动把某个技能的正文注入当前对话。不做技能注册表（design.md D30）。

## 3. 明确不做

这些在 v2 也不做。它们不是"以后再说"，是"不需要"。

| 条目 | 理由 |
|---|---|
| DAP 调试协议 | 用户用 dlv 命令行，不需要 agent 代劳 |
| 技能注册表 / 插件市场 | 注册表解决的是"别人写的技能怎么装到我这里"。li 只读本地 `.agents/skills`，没有分发环节。注意与 2.11 的"技能"区分：技能做，注册表不做 |
| 多机协作 / 直播 / 分享 | 单人使用 |
| 浏览器自动化 / 桌面控制 | 工作流里没有 |
| 语音合成与识别 | 同上 |
| Notebook 编辑 / Python 内核 | li 面对的是源码仓库 |

---

## 4. 版本节奏

v2 不在时间表上，只在条件上。

判定方式：每次开始一个新任务时问一句"这次有没有碰到 v2 清单里的触发条件"。碰到了，把它从本文档移到设计文档的决策区，按正常的设计流程走；没碰到，就继续用 v1。

这条规则的作用是防止两个常见的失败：过早加功能（把 v1 拖成半成品），和永远不加功能（需求已经变了还在忍着）。
